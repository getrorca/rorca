What was built:
- `spec_versions` table (SQLite) stores versioned snapshots of spec content with status and rejection reason
- `GET /api/specs/:specId/versions` returns all historical versions for a spec slug with metadata (version number, status, rejection reason, timestamp, title, story count)
- `GET /api/specs/:specId/diff?v1=N&v2=M` returns structured diff with per-story change type (added/removed/modified/unchanged) and per-field deltas for modified stories (including added/removed acceptance criteria)
- Rejected specs are now snapshotted into spec_versions before file deletion, preserving content + rejection reason
- Regenerating an existing slug auto-versions the old spec (no more 409 on duplicate slugs)

Key decisions:
- Versioning stored in SQLite (spec_versions table) rather than filesystem to keep it durable across file deletions
- Version numbers are monotonically increasing per spec_slug (not global)
- The versions endpoint doesn't require workspaceId since versions are keyed by spec_slug (global across workspaces)
- Changed generate behavior: regenerating same slug now versions the old file instead of returning 409 conflict
- Updated existing db.test.ts to expect 7 tables instead of 6

## Story US-002: Spec Template System — DONE
Files touched:
- backend/src/db/migrations/004_templates.sql (new)
- backend/src/routes/templates.ts (new)
- backend/src/routes/specs.ts (modified — templateId in generate)
- backend/src/server.ts (modified — mount templates router)
- backend/src/routes/__tests__/templates.test.ts (new — 19 tests)
- backend/src/db/__tests__/db.test.ts (modified — expect 8 tables)

What was built:
- `templates` table (SQLite) stores reusable spec structures with name, description, source_spec_id, brief, story_structure JSON, direction_layers JSON, story_count
- `POST /api/templates` creates a template from an approved spec's brief and story structure
- `GET /api/templates` lists all templates with summary fields (name, description, sourceSpecId, storyCount, createdAt)
- `GET /api/templates/:id` returns full template details including storyStructure and brief
- `DELETE /api/templates/:id` removes a template (returns 204)
- `POST /api/specs/generate` accepts optional `templateId` that injects the template's brief + story structure as a "REFERENCE TEMPLATE" section in the LLM prompt

Key decisions:
- Templates are workspace-agnostic (no workspace_id FK) — available across all workspaces per AC
- Template stores story structure as stripped-down array (id, title, description) not full stories with AC/deps
- When templateId is provided to generate, it adds the template as context before the task instructions, not as a hard constraint — LLM adapts the pattern to the new brief
- If templateId references a nonexistent template, generation proceeds normally without template context (graceful degradation)
- Updated db.test.ts to expect 8 tables instead of 7

## Gotchas Discovered
- Pipeline runs failed at 0ms: two bugs in ArchivePanel path construction (wrong subdir + using specName instead of id slug)
- xterm.js: must use scoped @xterm/xterm package, not legacy xterm
- gtimeout --foreground is REQUIRED in run-loop.sh — without it child process gets SIGTTOU → stopped state → 0-byte logs
- ALL 4 Claude env vars must be unset for nested invocation (not just CLAUDECODE)
- Port 3030 EADDRINUSE: always kill old process before restart (lsof -ti:3030 | xargs kill -9)
- Stale pipeline_runs: status stays 'running' after backend restart — UPDATE to failed manually
