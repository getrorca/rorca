# GitHub App integration adversarial review

Review scope: repository changes on `feat/github-app-integration` only. No live service, GitHub, infrastructure, DNS, database, policy, merge, deployment, or remote operation was performed.

| Threat | Attack considered | Control / result |
|---|---|---|
| Secret leakage | Private key, webhook secret, App JWT, installation token, or provider request-derived body enters DB metadata, WAL, audit details, logs, API/UI responses, errors, or test snapshots. | Private key/webhook secret use AES-256-GCM integration-vault rows. JWT/token are local variables or bounded in-memory cache only. One shared extractor never reads failed provider bodies and retains only status, stable code, validated GitHub request id, and a short generic message, including autonomous exact-SHA merge failure closeout. Metadata excludes token. Runtime/static tests inject body/secret material and assert it cannot reach terminal reasons, event details, or other sink values. |
| Confused deputy | Caller asks a workspace credential to operate on a different owner/repository or installation, or forges a WAL event for another run/workspace. | Resolver derives/compares exact workspace binding. Token request contains one repository id. Provider requires GitHub's response to list exactly that repository, then verifies repository id and full name with the issued token. App/installation/account/repository identity is server-validated. Governing Check/status posters accept only exact host-outbox rows, bind the event workspace/run/spec/story to canonical rows, and complete every local authority check before token resolution. Public WAL is always untrusted and workspace-member-scoped as defense in depth. |
| Stale token | Expired/near-expiry token is reused, concurrent refreshes race, or one permission profile satisfies another. | Cache is process-only, max 256 entries, 60-second skew, and keyed by immutable binding plus exact normalized permission profile. Refresh is single-flight per profile. Installation/repository identity is revalidated on refresh. GitHub revocation remains provider-enforced during the short token lifetime. |
| Installation drift | App id, account, selection mode, suspension, repository id/name, permissions/events, or hook activity change. | Refresh checks installation/repository identity and exact permissions; authoritative provider 401/403/404/410/422 failures invalidate the binding. Provider profile/hook verification expires after 24 hours, and stale state cannot report credential readiness until admin revalidation succeeds. |
| Replay/crash/redelivery | Two deliveries race, processing crashes after claim, an integrated-pass result commits before local pass projection, local pass commits before event relay, or a handler fails after earlier at-least-once side effects. | Integrated-pass delivery uses one versioned workspace/run/story/integrated-SHA key and the host engine's canonical DB transaction. That transaction writes the complete immutable result, exact integrated commit, one `story_result_id`-keyed accounting projection, and one exact trusted pass outbox row before local pass mutation. Semantic conflicts throw without fallback; transient failures are journaled only at the immutable run root and still throw. The untrusted journal cannot mint governing WAL: it can relay only an exact pre-existing trusted reference. Local pass releases the outbox, then relay occurs; duplicate/local-already-passed re-finalization releases the same one-to-one outbox, while startup recovery retries only released rows. Worker completion blocks on retained, invalid, malformed, incomplete, or failed critical recovery. Public WAL remains untrusted with exact duplicate identity. The webhook ledger separately retains its atomic bounded claim/reclaim and claim-token acknowledgement contract. |
| Multi-repo cross-talk | One App secret signs events for many repositories; an event routes to the wrong workspace. | App webhook routing requires active registration + installation + binding and exact installation id, repository id, owner/name, repository owner id/login. Unknown App identities never fall back to legacy webhook authority. DB unique/FK constraints prevent conflicting active identities. |
| Webhook forgery/abuse | Bad HMAC, modified bytes, missing headers, unsupported event, oversized body, or downgrade to a retained legacy secret. | Timing-safe SHA-256 HMAC over captured raw bytes, required bounded delivery id, 1 MiB Express/route/Traefik ceiling, and event allowlist. A current App binding (including disabled/invalid) rejects any payload that omits exact App installation/repository identity; the legacy row is transactionally retired on bind. Legacy `issues`/`check_run` compatibility remains accepted. |
| SSRF | Operator-controlled owner/repo, callback, manifest code, or IDs produce arbitrary outbound URLs. | Provider origin is hard-coded `https://api.github.com`; owner/repo have strict GitHub-compatible character bounds and path segments are encoded. Manifest endpoint/code is fixed and encoded. Callback must be configured HTTPS and non-local. |
| Callback CSRF/replay | Attacker swaps workspace/operator, replays state, or races two exchanges; a browser reload regenerates local CSRF state. | 256-bit random state stores only a SHA-256 digest, expires in 10 minutes, is bound to workspace and authenticated operator, and is atomically consumed before exchange. Normal CSRF middleware protects each local POST, but regenerated in-memory CSRF material is deliberately not callback identity. The callback targets `/settings/github`, works in a reload/new tab, and returns no private key to the browser. |
| Fallback escalation | Broken App binding silently falls back to broad workspace PAT/OAuth, a retained repository webhook, `github_connections`, or ambient `GITHUB_TOKEN`/`GH_TOKEN`. | One canonical repository-authority view makes any current App binding win; errors propagate and no credential/webhook fallback is consulted. Workspace PAT/OAuth is accepted only with active exact-repository legacy authority. Ambient and unscoped legacy-global credentials are never repository authority. |
| Model-granted authority | Model/MCP registers/installs/binds App, selects repo, activates policy, merges, or deploys. | Setup/import/bind/revalidate are actual workspace-admin middleware plus `x-rorca-tier: admin`, so excluded from MCP. UI requires explicit operator actions. No policy activation, merge, deployment, GitHub installation, or hook creation was added. Existing Lifecycle/provider evidence remains authoritative. |

## Fixes made during review

- Required the installation-token response to enumerate exactly one repository matching the immutable repository id, rather than trusting the request body alone.
- Requested and verified an exact purpose-specific token permission object, and isolated token cache/single-flight entries by that profile.
- Made webhook replay claiming atomic and boundedly reclaimable after failed/stale processing, with claim-token acknowledgement and provider-retry 503 responses.
- Prevented App webhook identity failures from falling through to the legacy PAT webhook path.
- Avoided `/user` validation for installation tokens and made disconnect disable the audit-retained App binding rather than mutate an App-global webhook.
- Added explicit admin revalidation plus audit-retained, immutable supersession for replacement bindings.
- Added canonical App-first repository authority for status/check posters, PR creation/update, delivery policy/evidence/merge, workflow routes/worker dispatch, CI autofix, health, and issue/spec discovery.
- Separated manual status context from autonomous evidence and bound the admin route to a workspace/run/PR/full-SHA provider check.
- Made final status/check publishers use full 40/64-hex object ids and exact workspace/run-scoped closeout rows populated from the verified integrated run-branch HEAD after no-ff merge; the story worktree parent and mutable HEAD cannot authorize final success. Crash-replayed integrated-pass finalization reuses one versioned deterministic result key, while one shared transaction now makes result, accounting, and exact commit projections atomic before local pass mutation. Failure injection covers both projection gaps, duplicate completeness/payload validation, and metadata-complete fallback replay.
- Added provider request timeouts, transaction-scoped secret insertion, exact PAT repository verification, and safe repository URL construction.

## Atomic story-result release-gate ledger (2026-07-18, F-02/F-03/F-04 remediation)

- The host engine uses one canonical helper transaction before local pass. It binds full result/commit/provenance identity and reasoning-only/cost-only accounting to one unique `story_result_id`; compatibility token/WAL writers can mutate only locked legacy unkeyed results.
- Transient direct-delivery failures journal at the immutable run root but still throw. Semantic conflicts never journal or fall back, and worker success is blocked by retained, invalid, malformed, incomplete, or failed critical recovery.

## F-06/F-07 webhook authority and administration remediation ledger (2026-07-18)

- Inbound GitHub App delivery now resolves current-binding presence first but takes dispatch authority only from `github_workspace_repository_authority`. A current disabled/invalid binding remains a legacy downgrade fence; only canonical `active` authority (active registration/installation/binding, unsuspended installation, exact permission/event profile, configured provider hook, and profile age no greater than 24 hours) can claim or dispatch. Exact signed installation, repository, and account identity remains mandatory. Signed stale/drifted/disabled traffic is rejected before claim and emits bounded rejection audit evidence without payload or secret material.
- Public webhook routing now mounts only strict, case-sensitive exact provider callback paths before auth. The reload-safe Manifest browser callback remains the static `GET /settings/github` route before API auth, while Manifest exchange remains protected. Raw-body capture and CSRF exemptions are limited to the four exact provider callback paths; `POST /api/webhooks/github` retains its 1 MiB parser/route bound. DLQ administration mounts after authentication and CSRF and remains default-denied/MCP-excluded.
- DLQ list requires a platform admin plus workspace membership and pins both list/count SQL to the requested workspace. Replay additionally requires workspace admin/owner authority, writes a durable workspace/operator audit intent before handler side effects, and passes the authorized workspace into replay. Replay does not need a fresh provider signature, but it joins the DLQ row to the exact failed delivery ledger on provider, delivery, event, workspace, payload SHA-256, verification method, and non-null signature-verification time. Cross-workspace, resolved, historical-unverified, changed-payload, or mismatched-ledger entries are indistinguishable from missing and are never returned to handlers.
- The fixed-clock repository-mismatch fixture remains deterministic. Historical DLQ rows are intentionally not granted verified provenance; only exact freshly authenticated delivery provenance is replayable.

## Trusted WAL/outbox remediation ledger (2026-07-18)

- Added `20260717100000_trusted_wal_outbox.sql`, after the prior latest prefix. It adds host/untrusted provenance, canonical run binding, immutable event identity, relay acknowledgement, a trusted-unrelayed index, and frozen expected story IDs. All explicit identifiers are at most 35 bytes.
- The execution engine and worker now persist governing events directly through the existing `wal_events` transaction/outbox boundary. The model child environment excludes database/PG host credentials and host process role; no callback capability or provider credential was added for WAL trust.
- Public `POST /api/wal` is explicitly untrusted, rejects the reserved deterministic outbox namespace, requires exact duplicate payload identity, and applies workspace membership middleware. Intentional local-admin fallback remains unchanged.
- Check Run and commit-status posters now reject untrusted, forged, cross-workspace, early, incomplete, wrong-state, and missing-closeout events before repository/token resolution. Success requires accepted latest pass results and exact host-integrated commits; run success additionally requires terminal canonical run state and a complete frozen latest-result set.
- Integrated pass now persists result + commit + trusted `story_passed` outbox atomically, carries the canonical run-derived `spec_id`, mutates the local spec only after commit, and relays afterward. Duplicate re-finalization and listener startup recover unacknowledged rows. Fallback governing records are relay-only exact references; compaction retains result-before-relay dependency order.
- Outbox readiness is released only after local pass. Startup/worker recovery retries only released rows; result fallback cannot mint governing WAL, while relay fallback can carry only an exact pre-existing trusted row reference.

## Final F1–F5 release-gate remediation ledger (2026-07-18)

- **F1 — host-only authority:** legacy `/api/pipeline/story-result` ingress is disabled unless explicitly enabled, requires authentication plus workspace-admin authority, and rejects every caller-supplied integrated/commit field before persistence. Immutable result provenance distinguishes host, compatibility, recovery proposal, and historical rows. Only the in-process execution engine can write a new integrated result. Terminal success now requires a host/execution-engine pass, exact accepted result/commit/closeout/outbox identity, one released trusted outbox, and a recomputed immutable event hash before repository or token resolution.
- **F2 — trusted refinalization:** integrated-pass journal fallback is proposal-only and cannot mint or release governing authority. `story-pass-recovery` scans unreleased host pass outboxes, requires a valid checkpoint attestation, exact run/workspace/spec/story/result/commit identity, deterministic run snapshot, exact repository root and branch HEAD, and then durably marks the local snapshot before releasing and relaying the existing outbox. Startup and worker completion invoke recovery; any drift, ambiguity, missing evidence, or recovery error remains a terminal blocker. Blocked retry snapshots are retained.
- **F3 — restart-safe Check Runs:** terminal Check Run intent is persisted in `github_check_run_projections` before trusted WAL acknowledgement. A claim-token lease, bounded backoff, stable external id, exact-SHA provider discovery, provider-uncertain reconciliation, and startup/periodic worker reconciliation make projection retryable across crashes. A terminal event supersedes an in-flight start safely, neutralizes a prior-head check when needed, and completes one exact-head provider Check Run. Failure results are persisted before trusted failure release; governing worker event persistence errors are no longer silently swallowed.
- **F4 — safe accounting upgrade:** the accounting backfill now accepts only non-negative integer counters, non-blank normalized models, and finite non-negative costs below the target `NUMERIC(18,6)` trillion-dollar boundary; malformed rows remain `NULL` for later reconciliation rather than aborting the migration. Historical integrated rows remain explicitly `legacy` and cannot satisfy terminal host authority.
- **F5 — normalized CSRF:** CSRF matching uses a bounded decoded pathname with case normalization, duplicate-slash collapse, and trailing-slash normalization. Any undecodable or suspicious `/api/*` pathname remains protected. Encoded-case and duplicate-slash DLQ replay variants are covered by real mounted middleware tests.

## Residual operational constraints

- App secret rotation is intentionally not improvised in this change. Until a separately reviewed rotation ceremony exists, follow the maintenance guidance in `docs/operations/github-app-setup.md`.
- Legacy PAT/OAuth and legacy per-repository webhook paths remain for migration compatibility. They do not override an existing App binding.
- A token already issued by GitHub may remain in memory until the short expiry/skew boundary; GitHub-side suspension/revocation is also expected to invalidate provider use. Rorca never persists it.
- Database migration execution was not run in this remediation because the task safety boundary forbids database/service mutation. Static contracts verify every explicit identifier is at most 63 bytes, matching first/remediation constraint names, dependency order, and reclaim schema. The safeguard was not bypassed.
- The OVH/Traefik files are review-only. They use observed `http`/`https` entrypoints, POST-only exact routing, and a separate Compose overlay joining `rorca_default` to external `coolify`; neither artifact has been applied.
