## 3. Implementation

### Backend changes
- `better-sqlite3` is **synchronous** — no async/await for DB calls
- `db.prepare(sql).get()` → T | undefined; `.all()` → T[]; `.run()` → RunResult
- Always enable WAL + FK on connection (already done in `db/index.ts` — don't duplicate)
- Emit `wal_events` for every state change — this drives the SSE pipeline and audit log
- **New tables**: numbered SQL migration files in `backend/src/db/migrations/` (next available: 039+). **Column additions**: SQLite lacks `ADD COLUMN IF NOT EXISTS` — use `pragma table_info` check in `backend/src/db/index.ts` instead of a migration file.
- `chatComplete()` returns `ChatResult { text: string; usage: TokenUsage }` — always use `.text`

### Frontend changes
- `apiFetch<T>(path, init?)` in `src/lib/apiFetch.ts` — use this for all API calls
- `useWorkspace()` provides `workspaceId`, `workspaces`, `selectedWorkspace`
- Panel components live in `src/panels/`, shared components in `src/components/`
- xterm.js: `@xterm/xterm` + `@xterm/addon-fit` (NOT the old `xterm` package)

### Critical path gotchas
- **Spec path**: `ralph/specs/approved/${spec.id}.json` (NOT `specs/approved/${spec.specName}.json`)
- **spec.id** = filename slug; **spec.specName** = human title (display only)
- **chatComplete** returns `ChatResult` — use `.text` accessor everywhere
- **Pipeline trigger** strips 4 Claude env vars before spawning `execution-engine.ts`
- **execution-engine.ts** (`backend/src/lib/execution-engine.ts`) is the universal TypeScript execution engine — handles claude, opencode, and codex agent paths. Replaces run-loop.sh/run-loop.ts entirely.
- **Backend port 3030** — restart required after any changes (`lsof -ti:3030 | xargs kill -9`)

Your task (EQ-014):
When Claude's subscription rate limit is hit during a parallel run, the affected story subprocess exits with a detectable error rather than being counted as a story failure. The worker pool catches this, parks the story in a retry queue with exponential backoff, and re-spawns it when the backoff timer expires — transparently, without user intervention. Rate limit retries do not count against `MAX_RETRIES`. The UI shows affected stories in an amber 'Rate limited — retry in Xs' state with a live countdown.

Acceptance Criteria:
- Rate limit detection in story subprocess wrapper: stderr contains 'rate limit exceeded' or 'overloaded' (case-insensitive), OR process exits with code 1 within < 5 seconds of start (heuristic for immediate rejection)  - On rate limit detection: do NOT call `markStoryFailed()` — instead emit WAL `story_rate_limited` event with `{ attempt: number, retryAfterMs: number }`  - Exponential backoff schedule: attempt 1 → 30s, attempt 2 → 60s, attempt 3 → 120s, attempt 4 → 240s. After 4 rate-limit attempts, mark story failed with `{ reason: 'rate_limit_exhausted' }`  - Rate limit retries are tracked separately from `MAX_RETRIES` (story logic errors) — both limits apply independently  - During backoff: story slot in the wave is parked — other stories in the wave continue running; the wave does not wait for the parked story before starting  - After backoff timer expires: re-spawn the story subprocess in the same worktree  - WAL `story_rate_limited` payload includes `{ storyId, attempt, retryAfterMs, waveIndex }` — visible in activity feed  - Run View UI: rate-limited story row shows amber background, clock icon, 'Rate limited — retry in Xs' with live countdown using SSE-driven state  - Countdown updates every second via a client-side timer seeded from the `retryAfterMs` in the WAL event — no additional SSE events needed for the tick  - On successful retry: story resumes normal pass/fail flow — row transitions from amber to blue (running) to green (passed)
