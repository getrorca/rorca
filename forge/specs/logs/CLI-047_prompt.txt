## Supabase Local Development

- Install the Supabase CLI first: `brew install supabase/tap/supabase`
- Initialize local config once with `supabase init` if the `supabase/` directory is missing
- Start services with `supabase start`
- Stop services with `supabase stop`
- Reset only the Supabase-managed local database with `supabase db reset`
- Frontend local URL is `http://127.0.0.1:54321`; Studio runs on `http://127.0.0.1:54323`
- For GitHub OAuth in local dev, set the callback URL in your GitHub OAuth app to `http://127.0.0.1:54321/auth/v1/callback`
- Rorca app schema migrations in `backend/src/db/pg-migrations/` are separate from Supabase CLI migrations in `supabase/migrations/`
- Warning: `supabase db reset` only runs `supabase/migrations/`; it does not apply `backend/src/db/pg-migrations/`. Use `npm run migrate` if available, or rely on `pg-index.ts` on backend startup for app schema migrations.

## Architecture

**Rorca** is a spec-driven development platform. It turns a plain-English brief into a structured spec (N user stories), then executes each story as an isolated subprocess with the full tool set — no context limits, resumable, runs to completion autonomously.

```
Browser (React :5210)  ←→  Express API (:3030)  ←→  PostgreSQL 16
                                                           ↑
                                                   Worker Process
                                                   (npm run worker)
                                                           ↓
                                                   execution-engine subprocesses
                                                   ├── claude --print
                                                   ├── opencode run
                                                   ├── codex
                                                   └── pi run --jsonl

Landing Page: Next.js 14 + Tailwind v4 + Framer Motion (:3002)
```

## Lite Mode

When DB mode is `native`, Apache AGE is not installed. Rorca still works, but graph-backed features are explicitly disabled and surface `503` with:
`{ error, code: 'AGE_NOT_INSTALLED', mode: 'lite', hint }`

Disabled in Lite Mode:
- `GET /api/specs/:specId/knowledge-graph` — spec review graph memory payload is unavailable.
- `POST /api/graph/populate` — graph population job cannot run without AGE.
- `POST /api/admin/graph-backfill` — admin graph backfill is unavailable.
- `GET /api/admin/graph-stats` — admin graph statistics are unavailable.
- `POST /api/workspaces/:id/drift/check` — graph-powered drift detection cannot run.
- Related-context expansion in story prompts — `graph-context.ts` returns no graph enrichment when AGE is unavailable.

Still available in Lite Mode:
- `GET /api/graph/stats` — returns `available: false` for lightweight capability/status checks.
- `GET /api/workspaces/:id/drift` — reads previously stored drift reports from PostgreSQL.
- `GET /api/specs/:specId/graph` — this is the story dependency DAG from spec JSON, not Apache AGE.
- Specs CRUD, runs, analytics, direction stack, and non-graph memory/search flows continue to work.

**Stack**:
- Frontend: React 18 + TypeScript + Vite + Tailwind CSS + xterm.js
- Backend: Express.js + TypeScript + PostgreSQL 16 (`pg` Pool, async, connection pooling, pgvector, Apache AGE)
- Execution: `claude --print` (Claude sub) OR `opencode run --format json --attach` (OpenCode, any provider) OR `codex exec --dangerously-bypass-approvals-and-sandbox` (ChatGPT sub) OR `pi run --jsonl` (pi subprocess)
- Spec generation: OpenCode (autonomous codebase exploration) OR SDK fallback (`SPEC_PROVIDER` env var)
- MCP: API-first (OpenAPI spec → auto-generated MCP tools via HTTP transport on :3030)

**Ports**: Frontend 5210, Backend 3030, FinOps sim 5200

## Execution Engine — Core Identity

Every story runs as a fresh isolated subprocess with the full tool set. No context limits. A spec can run forever.

```
Spec (N stories)
  └── Story 1  →  fresh agent subprocess  →  edit, bash, read, write, glob, grep  →  commit
  └── Story 2  →  fresh agent subprocess  →  edit, bash, read, write, glob, grep  →  commit
  └── Story N  →  ...
```

## Command Center Architecture

Rorca's command center is split into four layers so interactive control, orchestration state, headless execution, and observability stay decoupled:

| Layer | Role |
|-------|------|
| Forge TUI | Local control surface for `rorca forge`, `rorca chat`, approvals, and operator commands. |
| Engine `:3030` | Orchestration state machine: API, WAL, pg-boss queue, worker coordination, and persistence. |
| Muscle | Headless `pi` subprocesses that execute stories and chat tasks with the full tool set. |
| Observatory | Web UI for run state, logs, analytics, and architecture audit views. |

**BYOA model**: pi is bring-your-own-auth. `pi` manages provider auth locally, Rorca never stores pi API keys, and users run `pi auth login <provider>` once per provider on the machine that will execute runs.

### Dual-Mode Vision

| Mode | Entry Point | Purpose |
|------|-------------|---------|
| Interactive Chat | `rorca chat` | Operator-driven live sessions against the same local workspace context. |
| Autonomous Spec | `rorca run` | Queue and execute approved specs through the orchestration engine. |
| Architecture Audit | web Observatory | Inspect system state, traces, and architecture-level health from the browser UI. |

### Four execution paths — all first-class

**Claude subscription** (Pro / Max / Max 5x):
- Binary: `claude --print`
- Advantages: prompt caching on tool round trips (~10x lower latency after turn 1), surgical diff edits (~150 tokens vs ~3000 for full rewrites), persistent bash shell state across tool calls, CLAUDE.md auto-injection, hierarchical subagents (Task tool), fine-tuned for agentic coding loops
- Subscription tier affects rate limits only — Pro may throttle on 64+ story specs, Max/Max5x recommended for production

**OpenCode** (API key: any provider):
- Binary: `opencode run --model <provider>/<model> --format json --attach`
- Supports: OpenAI (GPT-4o, o3), Google (Gemini 2.0), Anthropic API, OpenRouter (75+ models), GitHub Copilot subscription, local Ollama (free)
- Same tool set: `edit` (surgical), `bash`, `read`, `write`, `glob`, `grep`, `webfetch`, `websearch`
- `--format json` outputs structured events → semantic log view gets structured data for free (no xterm parsing)
- `--attach` reuses a warm server across stories → no cold-start overhead per story
- Configured via `RORCA_AGENT=opencode` + `RORCA_MODEL=openai/gpt-4o`

**Codex CLI** (ChatGPT Plus/Pro subscription):
- Binary: `codex exec --dangerously-bypass-approvals-and-sandbox`
- Same tool set: file edit, bash, read, write, glob, grep (non-interactive mode)
- Subscription-based — flat rate, no per-token cost. `RORCA_MODEL` is ignored.
- No model cascading — single model tied to ChatGPT subscription
- Configured via `RORCA_AGENT=codex`

**pi CLI** (provider auth handled locally by pi):
- Package: `@mariozechner/pi-coding-agent`
- Install:
```bash
npm i -g @mariozechner/pi-coding-agent
pnpm add -g @mariozechner/pi-coding-agent
bun add -g @mariozechner/pi-coding-agent
curl -fsSL https://pi.run/install.sh | sh
```
- Binary invocation: `pi run --jsonl --skill <direction-file>`
- JSON-L events stream to stdout for engine ingestion
- Session controls: `--session`, `--fork`, and `--continue`
- Direction injection: `--skill` is the direction-stack injection path for pi runs
- Auth model: BYOA. Users run `pi auth login <provider>` once per provider; Rorca never stores pi API keys
- Recommended for: Headless provider-flexible runs with pi-managed auth and resumable session/fork workflows

### Pi peer dependency

`pi` is intentionally a peer dependency, not bundled with Rorca. Rationale: bundling adds unnecessary 50-100MB tarball weight, and silent auto-download would remove user agency around what gets installed on the machine.

The install bridge is detect + prompt:
- `rorca init` checks for `pi` first and offers npm/pnpm/bun/curl install options
- `rorca auth login` does the same before attempting provider login
- `rorca init --auto-install-pi` exists for CI and other non-interactive environments
- The curl path always requires an explicit confirmation prompt before execution

**No raw SDK agent path for execution.** Claude, OpenCode, Codex, and pi are the supported execution harnesses. A raw SDK call cannot replace them — no persistent bash state, no surgical edits, no harness-native context injection.

### OpenCode for spec generation
OpenCode also handles spec generation (not just execution). Spec gen benefits from tools: `glob` existing specs, `read` CLAUDE.md, `grep` codebase patterns, `webfetch` library docs. This makes specs dramatically more context-aware than a blind API call and replaces the manual context extraction step.

## Key Concepts

### Direction Stack (5-layer context cascade)
| Layer | Scope | Content |
|-------|-------|---------|
| L1 | Global (all workspaces) | Engineering principles, preferred libraries |
| L2 | Domain (e.g. "saas") | Auth patterns, API conventions |
| L3 | Project (one workspace) | Stack, architecture, key constraints |
| L4 | Spec brief | What this feature is and why |
| L5 | Story annotations | Edge cases, reviewer notes |

Lower layers override higher ones (like CSS specificity). L1–L2 are globals; L3+ are per-workspace.

### Spec Lifecycle
`Spec Forge → Review Queue → Approved → Pipeline Run → Archive`

Spec files live in the **project workspace** (not Rorca):
- Pending: `<workspace>/forge/specs/pending/<slug>.json`
- Approved: `<workspace>/forge/specs/approved/<slug>.json`

### Spec JSON format
```json
{
  "title": "my-spec-slug",
  "userStories": [
    {
      "id": "US-001",
      "title": "...",
      "description": "...",
      "acceptanceCriteria": ["..."],
      "dependsOn": [],
      "passes": false
    }
  ],
  "model": "claude-sonnet-4-5-20250929",
  "generatedAt": "2026-02-23T..."
}
```
⚠️ Key field is `userStories` (NOT `stories`). `id` is always the slug (filename without `.json`), NOT the human-readable title.

### Job Queue Architecture (pg-boss)

Pipeline runs are no longer spawned synchronously by `pipeline.ts`. The flow is:

1. `POST /api/pipeline/trigger` inserts a `pipeline:run` job into pg-boss and returns `{ runId, queued: true, queuePosition }` in ~200ms
2. The **Worker process** (`backend/src/worker.ts`, `npm run worker`) polls pg-boss and picks up the job ~500ms later (default polling interval, configurable via `pollingIntervalSeconds`)
3. Worker spawns `execution-engine.ts` as a child process with `RORCA_PROCESS_ROLE=engine`

**Job types**:
| Queue | Purpose |
|-------|---------|
| `pipeline:run` | Trigger a new pipeline run (specPath, workspaceId, runId, options) |
| `pipeline:retry` | Retry failed stories in a completed run (runId, storyIds) |
| `pipeline:cancel` | Cancel an active run by sending SIGTERM to the child process |
| `pipeline:cron` | Meta-cron tick — checks `pipeline_schedules` for due runs |
| `pipeline:cron:<id>` | Per-schedule cron job — fires a specific scheduled run |

**Worker process** (`backend/src/worker.ts`):
- Standalone process — completely independent of Express API
- Connects to the same `DATABASE_URL` as the API
- Writes heartbeat to `worker_heartbeat` table every 30s (`worker_id`, `pid`, `hostname`, `last_seen`)
- Graceful shutdown on `SIGTERM` — drains in-flight jobs up to 30s before exiting
- `RORCA_PROCESS_ROLE=engine` is set in the child process env to prevent nested worker spawning

**Terminal output streaming** (`run_output_chunks`):
- Worker writes stdout/stderr to `run_output_chunks` table in 4KB chunks with monotonically increasing sequence numbers
- DB-backed streaming survives backend restarts and enables late-join SSE replay
- `GET /api/pipeline/runs/:runId/output` SSE endpoint replays all chunks since sequence 0, then streams live

### The Ralph Loop (`backend/src/lib/execution-engine.ts`)
The sole execution engine is `backend/src/lib/execution-engine.ts` — TypeScript, cross-platform, spawned by the **Worker process** (not directly by `pipeline.ts`). The legacy `forge/run-loop.sh` (in each project workspace) is a bash fallback — only used if `execution-engine.ts` is somehow missing. `run-loop.ts` has been deleted — `execution-engine.ts` is a strict superset covering all four agent types. **Always edit `execution-engine.ts` for all execution behavior.**

**Flags**: `--json <path>` (spec file), `--cwd <path>` (workspace root), `--run-id <number>` (required for WAL events), `--story <ID>` (single story), `--dry-run` (preview only), `--port <number>` (default 3030), `--agent <claude|opencode|codex|pi>`, `--model <model>`

**Modes** (auto-detected from JSON structure):
- Implementation (`impl`): `{ userStories: [...] }` — injects `.claude/skills/rorca.md`, `feat:` commits
- QA (`qa`): `{ phases: [{ stories: [...] }] }` — test-writing prompt, `test:` commits
- Journey (`journey`): `{ mode: "journey", ... }` — user simulation prompt, `journey:` commits

**What `execution-engine.ts` does per story**:
1. `emitWalEvent('story_started')` via `fetch` to `/api/wal`
2. Spawns agent subprocess (`claude --print`, `opencode run`, `codex`, or `pi`) with clean env
3. Timeout via SIGTERM → SIGKILL after 10s
4. On exit 0: `markStoryPassed()` (writes spec JSON), `gitCommitStory()`, `emitWalEvent('story_passed')`, POST to `/api/pipeline/story-result`
5. On exit 124 (timeout): `markStorySkipped()`, `emitWalEvent('story_failed', { reason: 'timeout' })`
6. On non-zero: retry up to `MAX_RETRIES=3` with optional model escalation (Haiku→Sonnet→Opus for OpenCode), then skip with `emitWalEvent('story_failed', { reason: 'max_retries' })`

**Context injected** by `buildPrompt()` from the workspace `cwd`:
- `.claude/skills/rorca.md` — workflow skill (falls back to `dimitri.md`)
- `.rorca/personas/` — persona files matched to story via PersonaRegistry
- `.rorca/config.json` — context routing rules (micromatch path scoping)
- `MEMORY.md` — episodic ledger injected per story
- `AGENTS.md` — file governance rules
- LLM-matched skill files from SkillRegistry
- `CLAUDE.md` is injected automatically by `claude --print` (not manually by execution-engine.ts)

PostgreSQL enforces FK constraints natively. Connection pooling (max 20, 30s idle timeout) is configured in `backend/src/db/index.ts`.

## Backend Infrastructure

Key `backend/src/lib/` modules beyond `llm-client` and `direction-stack`:

- **`sse-hub.ts`** — Centralized pub/sub for WAL events. `broadcastAll(event)` fans out to all subscribers. `attachSSE(res)` wires an Express response. `subscribe(fn)` is used by `agent-hook-runner` and `notification-dispatcher` too — not just HTTP clients.
- **`errors.ts`** — `AppError` class hierarchy: `ValidationError` (400), `AuthError` (401), `ForbiddenError` (403), `NotFoundError` (404), `ConflictError` (409), `UnprocessableError` (422). Throw these from route handlers; `error-handler.ts` catches and serializes to `{ error, code, details }`.
- **`scheduler.ts`** — Cron job runner for `pipeline_schedules`. Calls pipeline trigger internally.
- **`agent-hook-runner.ts`** — Subscribes to SSE hub; fires agent hooks on WAL events matching configured patterns.
- **`notification-dispatcher.ts`** — Subscribes to SSE hub; routes WAL events to email/webhook/in-app notification channels.
- **`rate-limiter.ts`** — In-memory sliding window, keyed `userId:method:path` (authenticated) or `ip:method:path` (unauthenticated). Limits are loaded from the `rate_limits` DB table (30s cache); defaults: 100 req/min authenticated, 20 req/min unauthenticated. To change limits: `UPDATE rate_limits SET max_requests=500 WHERE tier='authenticated'` then call `invalidateRateLimitCache()` or restart backend. Skipped in `NODE_ENV=test` unless `RATE_LIMIT_ENABLED=true`.
- **`paginate.ts`** — Standard `{ items, total, page, pageSize }` helper for paginated routes.
- **`swagger.ts`** — Auto-generates OpenAPI spec from JSDoc `@swagger` annotations. Served at `/api/docs`.
- **`context-router.ts`** — CIE virtual context payload compiler. `route(story, config, workspacePath, monorepoApps?)` assembles story-specific context: matches story paths via micromatch, resolves priority conflicts (highest wins), enforces token budget (globals = priority 101, never dropped). `detectCrossAppPaths()` synthesizes paths from monorepo app names mentioned in story text. `writeContextFile()` emits a temp file including the memory ledger section if `workspacePath` is provided. Token estimate: `text.length / 4` chars (±10%).
- **`workspace-echolocation.ts`** — Workspace intelligence scanner. `echolocate(path)` → `EcholocationReport` detects stack (80+ npm packages, Cargo.toml, requirements.txt, go.mod, Dockerfile), context files, monorepo structure, and computes weighted health score (CLAUDE.md 30pt, AGENTS.md 20pt, config.json 20pt, MEMORY.md 15pt, skills 15pt). `discoverMonorepo()` scans `apps/`, `packages/`, `libs/`, `services/`, `modules/` for manifests. `inferSkillsFromStack()` maps detected tech names to skill filenames via `STACK_TO_SKILLS` lookup. Health penalty: CLAUDE.md < 10 lines = half credit, < 50 lines = 75% credit.

## Critical Gotchas

### Top 6
1. **`chatComplete` returns `ChatResult { text, usage }`** — always use `.text` accessor. Never treat result as a string.
2. **pg is async — always `await` DB calls**. `await queryOne<T>(sql, params)` returns T|undefined, `await query<T>(sql, params)` returns T[], `await execute(sql, params)` returns `{ rowCount }`. Use `$1, $2, ...` numbered placeholders (not `?`).
3. **spec `id` ≠ spec `specName`** — `id` is the filename slug (`rorca-feature-enhancements`), `specName` is the human title. Use `spec.id` to construct file paths.
4. **run-loop.sh is a bash fallback only** — lives at `workspace.path/forge/run-loop.sh`. Only used if `execution-engine.ts` is missing. Claude-only, no multi-agent support. Do not rely on it.
5. **Backend auto-restarts** — `tsx watch` detects file changes and restarts automatically. Manual restart only needed if the process itself crashes: `lsof -ti:3030 | xargs kill -9 && cd backend && npm run dev`.
6. **Worker must be running** — pipeline triggers insert a pg-boss job and return immediately; runs only execute if the worker process is live. Check `GET /api/pipeline/worker/health` before triggering runs. Start with `cd backend && npm run worker` or `npm run dev` (starts both). Stale if `worker_heartbeat.last_seen` > 90s.

### Auth Middleware — Intentionally Bypassed
`app.use(authRequired)` in `backend/src/server.ts` line ~78 is **commented out**. This is intentional — Rorca is a local single-user tool and the login wall blocks workspaces API causing onboarding to show incorrectly. Do NOT re-enable globally. Auth routes (`/api/auth/*`) still work for the registered user (`admin@rorca.local` / `rorca123`). If authRequired reappears as a global middleware, comment it out again.

### Stale Pipeline Runs

```sql
-- Fix
UPDATE pipeline_runs SET status='failed', finished_at=NOW() WHERE status='running' AND id=<id>;
```

### WAL Events Table — Column Is `ts`, Not `created_at`
The `wal_events` table uses `ts` as the timestamp column — NOT `created_at`. Queries against this table must use `ORDER BY ts DESC` and `SELECT ts`. The route handler can alias it (`ts AS created_at`) for API consumers, but the SQL itself must use `ts`. Using `created_at` produces an error: no such column.

### Apache AGE — Pool Connection Hygiene (CRITICAL)
Apache AGE requires `LOAD 'age'` + `SET search_path = ag_catalog, "$user", public` per session before Cypher queries. This **poisons** the pool connection — subsequent queries on that connection hit `ag_catalog.workspaces` (empty) instead of `rorca.workspaces` (real data), causing intermittent "Workspace not found" 404s.

**Rule**: Any code that calls `setupAgeSession()` MUST restore the search_path before releasing:
```typescript
const client = await pool.connect();
try {
  await setupAgeSession(client);  // sets search_path to ag_catalog
  await client.query(cypherSQL);
} finally {
  await client.query('SET search_path = rorca, public');  // MUST restore
  client.release();
}
```

Three schemas have a `workspaces` table: `rorca.workspaces` (app data), `ag_catalog.workspaces` (AGE system, empty), `public.workspaces` (legacy, empty). The pool has an `on('connect')` safety net in `db/index.ts`, but it does NOT replace proper cleanup in graph code.

### PostgreSQL Migration Pattern — Timestamp Format (CRITICAL)
Migrations are SQL files in `backend/src/db/pg-migrations/`. They run in numeric prefix order on first startup via `pg-index.ts`, tracked in `schema_migrations` table (BIGINT version column). Each migration runs inside a transaction. PostgreSQL supports `IF NOT EXISTS` for `CREATE TABLE`, `ADD COLUMN`, and indexes natively.

**New migrations MUST use timestamp format**: `YYYYMMDDHHMMSS_description.sql`
```bash
# Example: creating a migration on 2026-03-14 at 15:00:00
20260314150000_add_user_preferences.sql
```

**Why**: Sequential numbers (001, 002, ...) collide when parallel branches create migrations simultaneously — common with Rorca's worktree-per-spec architecture. Timestamps are structurally unique (two developers/agents can't commit at the exact same second).

**Hybrid coexistence**: Existing sequential migrations (001–079) stay as-is. New timestamp migrations sort after them automatically (numeric sort: `79 < 20260314150000`). The runner supports both formats indefinitely — no renaming needed.

**Duplicate prefix detection**: `pg-index.ts` calls `checkDuplicatePrefixes()` at startup and fails loudly if two files share the same numeric prefix. This catches collisions before any SQL runs.

### Skills Install Chain (install-from-sh)
`POST /api/skills/install-from-sh` does NOT shell out to `npx skills add`. It fetches directly:
1. Search `https://skills.sh/api/search?q={name}` → gets `{ skillId, source }` where `source` = GitHub owner/repo (e.g., `vercel-labs/agent-skills`)

The `anthropics/skills` repo only contains docx/pdf/pptx/xlsx tools — not generic web skills. Generic skills (react, node, tailwind) come from `vercel-labs/agent-skills`, `wshobson/agents`, etc. Never hardcode GitHub source repos.

### node-pty Native Module — Terminal Feature Dependency (CRITICAL)
`node-pty` is a native N-API module required for the OpenCode terminal feature (OCT-001–OCT-004). It requires compiled binaries per platform.

**Graceful degradation**: `pty-manager.ts` wraps the `require('node-pty')` in a try/catch at module load. If the import fails:
- `PTY_AVAILABLE` flag is set to `false`
- `POST /api/terminal/sessions` returns `503 Service Unavailable` with error code `PTY_NOT_AVAILABLE`
- Response includes hint: `"cd backend && npm rebuild node-pty"`
- Backend starts successfully (terminal feature disabled, all other routes work)

**Installation**:
```bash
cd backend && npm install  # Triggers postinstall probe
npm rebuild node-pty       # Rebuild if probe fails
```

**Distribution constraint**: `node-pty` **cannot** be bundled with `bun build --compile` (DIST-001–DIST-010). Native N-API modules require a real `node_modules/` directory on disk. The terminal feature is **server-only** and requires either:
- Users run `npm rebuild node-pty` after install (documented in install script)
- Future Electron/Tauri packaging handles native modules automatically

**Prebuild binaries**: `node-pty` v1.1.0+ ships prebuilt binaries for common platforms (macOS arm64/x64, Linux x64/arm64, Windows x64). The `backend/node_modules/node-pty/prebuilds/` directory is excluded from git (platform-specific, rebuilt on install).

**Testing**: Backend starts even when node-pty is not built. Create a PTY session to verify — should return 503 if module unavailable, 201 if working.

### WebSocket Security Model (OCT-021)
The `/ws/terminal` WebSocket endpoint is hardened against cross-origin attacks. With Rorca's auth bypassed, an unauthenticated WebSocket would be a remote code execution vector accessible from any local webpage via DNS rebinding.

**Security layers**:
1. **Origin validation** — `verifyClient` callback rejects connections from disallowed origins. Allowed: `http://localhost:5210`, `http://127.0.0.1:5210`, `http://localhost:3030`, `http://127.0.0.1:3030`. Rejected: any other origin with 403 Forbidden.
2. **Short-lived connection tokens** — `POST /api/terminal/sessions` returns `wsToken` (UUID, 60s TTL). WebSocket URL is `/ws/terminal?wsToken=<token>` (NOT `?sessionId=<id>`). Server validates token, maps to sessionId, then deletes (one-time use). Prevents sessionId enumeration.
3. **Secure binding** — HTTP server binds to `127.0.0.1` by default (local-only). `RORCA_BIND_HOST` env var can override (e.g., `0.0.0.0` for Docker/cloud). Production deployments should keep `127.0.0.1` and use nginx/Cloudflare for TLS termination.
4. **Security headers** — WebSocket upgrade response includes `X-Content-Type-Options: nosniff` and `X-Frame-Options: DENY`.

**Token lifecycle**:
- Generated: `POST /api/terminal/sessions` → `{ sessionId, wsToken, ... }`
- Validated: WebSocket client connects with `?wsToken=<token>` → server looks up sessionId from token map, deletes token (one-time use)
- Expired: Tokens older than 60s are rejected; background cleanup runs every 30s

**Why this matters**: Without these guards, a malicious webpage at `http://evil.local:8080` could open a WebSocket to `ws://localhost:3030/ws/terminal?sessionId=<guessed-uuid>` and execute arbitrary commands in the user's terminal. Origin validation blocks this. Connection tokens prevent sessionId brute-force.

### MCP Architecture — API-First, MCP-Second
Rorca follows an **API-first** approach: Express routes are the source of truth, MCP tools are auto-generated from the OpenAPI spec. This eliminates hand-written MCP wrappers and version skew.

```
Express API routes → @swagger JSDoc annotations → OpenAPI spec (/api/docs/openapi.json)
                                                → MCP auto-generated from OpenAPI
                                                → Served over HTTP on same :3030 port
```

**Current state**: 24 hand-written stdio MCP tools in `backend/src/mcp/server.ts`.

**Bridge URL**: HTTP MCP transport is mounted at `http://localhost:3030/mcp` when `RORCA_SERVE_MCP` is unset or not equal to `false`. `RORCA_SERVE_MCP=false` disables the HTTP bridge and its local OAuth helper routes; Pi chat sessions then run without Rorca MCP tools.

Security: `/mcp` now requires `Authorization: Bearer <token>` where the token is stored at `~/.rorca/mcp-token` with mode `0600`. The backend generates this token at startup. Never log or commit it.

### MCP Security Model (CLI-046)
By default, MCP is **localhost-only** even when the main API is intentionally bound to `0.0.0.0` via `RORCA_BIND_HOST`. The `/mcp` routes enforce two layers:
1. **CORS lockdown** — browser requests are allowed only from `http://localhost:3030` and `http://127.0.0.1:3030`. Server-to-server clients like Claude Code, curl, and stdio bridges typically send no `Origin` header and are allowed. Drive-by browser requests from `https://evil.com` are rejected at the CORS layer before auth runs.
2. **Loopback gate** — `/mcp` rejects any non-local socket address unless `RORCA_MCP_ALLOW_REMOTE=true`. Accepted loopback forms are `127.0.0.1`, `::1`, and `::ffff:127.0.0.1`.

Remote MCP is an explicit escape hatch:
- Set `RORCA_MCP_ALLOW_REMOTE=true` only behind a trusted TLS terminator or auth proxy.
- That proxy must validate and sanitize `Authorization` header forwarding to prevent header smuggling or accidental token passthrough from untrusted clients.
- If remote MCP is enabled, configure Express `trust proxy` only in that trusted deployment shape so forwarded client IPs are meaningful.
- Rotate the MCP bearer token regularly with `rorca mcp rotate-token`.
- Review `mcp_audit_log` entries from CLI-051 as part of ongoing security monitoring.

Asymmetry note: a localhost-gate failure returns structured JSON (`403 MCP_REMOTE_FORBIDDEN`), but a CORS denial comes from the `cors` middleware callback and surfaces as a generic CORS/network failure in browsers rather than the standard API JSON schema.

### Execution Engine: Claude vs OpenCode vs Codex vs pi

Rorca supports four first-class execution paths. All use the same tool set (edit, bash, read, write, glob, grep, webfetch, websearch) and produce the same output contract.

**Claude subscription** (`RORCA_AGENT=claude`, default):
- Binary: `claude --print --dangerously-skip-permissions --output-format stream-json`
- Auth: `~/.claude/` — no API key needed, uses your Pro/Max/Max5x subscription
- Advantages:
  - **Prompt caching** on tool round trips (~10x lower latency after turn 1)
  - **Surgical diff edits** (~150 tokens vs ~3000 for full file rewrites)
  - **Persistent bash shell state** across tool calls within a story
  - **CLAUDE.md auto-injection** — no manual context loading needed
  - **Hierarchical subagents** via Task tool for complex research
  - **Fine-tuned** for agentic coding loops (tool use, error recovery, commit discipline)
- Recommended for: All implementation runs where Claude subscription is available

**OpenCode** (`RORCA_AGENT=opencode`):
- Binary: `opencode run --format json --attach --model $RORCA_MODEL`
- Auth: Per-provider API key (stored in encrypted vault) or GitHub Copilot OAuth
- Advantages:
  - **75+ model choices** — OpenAI, Google, Anthropic API, OpenRouter, Ollama, GitHub Copilot
  - **Model cascading** — auto-tier stories by complexity (Haiku→Sonnet→Opus), saves ~40-60% vs all-Opus
  - **API arbitrage** — choose cheapest model that meets quality bar per story
  - **Local execution** via Ollama (free, fully offline, no API key)
  - **Subscription-based** execution via GitHub Copilot (no per-token billing)
  - **Structured JSON events** — semantic log view gets structured data natively (no xterm parsing)
  - **Warm server mode** — `--attach` reuses a warm server across stories, no cold-start per story
- Recommended for: Multi-model workflows, cost optimization, teams without Claude subscription

**Codex CLI** (`RORCA_AGENT=codex`):
- Binary: `codex exec --dangerously-bypass-approvals-and-sandbox`
- Auth: ChatGPT Plus/Pro subscription — no API key needed
- Advantages:
  - **Subscription-based** — flat-rate, no per-token cost (like Claude subscription)
  - **Same tool set** — file edit, bash, read, write, glob, grep via `--approval-mode auto-edit`
  - **OpenAI models** — uses the model tied to your ChatGPT subscription
- Limitations:
  - `RORCA_MODEL` is ignored — Codex CLI uses the model from your ChatGPT subscription
  - **No model cascading** — subscription-based, no tier assignment or escalation
  - **No structured JSON output** — stdout/stderr captured raw (like `claude --print`)
  - FinOps shows token counts only (no dollar cost — flat-rate subscription)
- Recommended for: Teams with ChatGPT Plus/Pro subscriptions who prefer OpenAI models

**pi CLI** (`RORCA_AGENT=pi`):
- Binary: `pi run --jsonl --skill <direction-file>`
- Auth: BYOA via local pi auth state. Users run `pi auth login <provider>` once per provider; Rorca never stores pi API keys
- Advantages:
  - **JSON-L events** — structured stdout stream for orchestration, logs, and replay
  - **Session branching** — `--session`, `--fork`, and `--continue` support resumable and branchable runs
  - **Skill injection** — `--skill` maps cleanly to synthesized direction-stack context
  - **Provider-local auth** — provider credentials stay in pi's local auth store instead of the Rorca vault
- Recommended for: Local-first headless execution with pi-managed sessions and provider auth

### Codex Direction Stack Injection (OC-030)
Codex CLI auto-discovers `AGENTS.md` files from the Git root directory and injects them as context before the user prompt (see [OpenAI docs](https://developers.openai.com/codex/guides/agents-md/)). Rorca leverages this by writing the synthesized direction stack (L1-L5) to the workspace root `AGENTS.md` before each Codex pipeline run.

**How it works:**
- `pipeline.ts` calls `writeCodexAgentsMd()` before spawning the execution engine when `RORCA_AGENT=codex`
- Synthesizes L1-L5 direction layers (same `synthesize()` call used for OpenCode's `.opencode/skills/rorca/SKILL.md`)
- If workspace already has `AGENTS.md`: appends a delimited section using markers (`# === RORCA DIRECTION START ===` / `# === RORCA DIRECTION END ===`)
- If no `AGENTS.md` exists: creates one with just the direction stack section
- Direction context is written fresh before each run (not cached) to pick up latest direction stack changes
- On run completion (pass or fail), `removeCodexAgentsMd()` restores the original `AGENTS.md` or deletes the file if Rorca created it
- `execution-engine.ts` `buildPrompt()` adds an explicit instruction for Codex stories to follow AGENTS.md guidance

**Key difference from OpenCode:** OpenCode uses `.opencode/skills/rorca/SKILL.md` (a dedicated skill file in a hidden directory). Codex uses the workspace root `AGENTS.md` because that's what Codex CLI auto-discovers. The marker-based append/restore pattern ensures existing `AGENTS.md` content is preserved.

### Model Cascading (added by rorca-opencode-integration OC-019–OC-020)
When OpenCode is the execution engine, a Story Complexity Scorer automatically assigns ModelTier before each subprocess spawn:

```
ModelTier assignment (scored from story metadata):
  Haiku   → simple CRUD, UI copy, config tweaks, low dependsOn depth
  Sonnet  → standard features, moderate file count, some business logic
  Opus    → architecture, security, payments, high dependsOn depth

Escalation cascade on failure:
  Haiku fails 2×  →  retry with Sonnet
  Sonnet fails 2× →  retry with Opus
  Opus fails      →  mark story_failed, notify user
```

**API arbitrage**: Cascading saves ~40–60% vs all-Opus baseline. FinOps dashboard (OC-023) shows realized savings per run and trend chart.

**Claude/Codex subscription paths**: Cascading not applicable — `claude --print` and `codex exec --dangerously-bypass-approvals-and-sandbox` use the same subscription regardless of story complexity. Quality difference is negligible for most stories; Opus is the recommended tier for all implementation runs.

## Context/Intent Engine Architecture (rorca-context-intent-engine)

**Philosophical split**: Context = "The Is" (what the codebase IS — CLAUDE.md, file structure, patterns). Intent = "The Ought" (what should be built — spec JSON, direction stack, story goals). Rorca bridges both.

```
Is (Context/Ontology)          Ought (Intent/Teleology)
──────────────────────         ──────────────────────────
CLAUDE.md                      Spec JSON (userStories)
.rorca/config.json            Direction Stack (L1–L5)
AGENTS.md (file governance)    Story annotations (L5)
run-state.json                 Brief → spec pipeline
MEMORY.md (ledger)
```

### .rorca/ directory (introduced by CIE spec)
```
.rorca/
├── config.json          # Orchestration config (routing, cascades, wave parallelism)
├── MEMORY.md            # Episodic ledger — timestamped structured rules (NOT prose)
├── AGENTS.md            # Soft governance: file ownership, behavioral rules per area
└── skills/              # Skill library (reusable rorca.md snippets)
```

### Key CIE concepts
- **Virtual context routing**: `config.json` routing table with path glob scoping. `micromatch`-based path prediction assigns right context slices to right stories. No file scatter.
- **Episodic MEMORY.md ledger**: Structured timestamped rule entries, not prose. Categories: Architecture, Convention, Bug Fix, Decision, Pattern, Gotcha. Post-run synthesis adds entries automatically.
- **AGENTS.md as soft governance**: File ownership + behavioral rules injected into prompts. NOT hard filesystem RBAC (too complex for v1).
- **run-state.json**: Typed event ledger replacing `progress.txt`. Atomic writes, deterministic resume across compaction.
- **"Eject to Config"**: Progressive disclosure — `.rorca/config.json` generated on demand for advanced users who want to customize routing, thresholds, or cascades.
- **Chokidar file watchers**: Real-time filesystem → UI sync when users edit context files externally. Bi-directional Direction Stack ↔ CLAUDE.md sync with approval.
- **Trojan horse strategy**: Rorca's filesystem-native output (CLAUDE.md, MEMORY.md, AGENTS.md) makes ALL other AI tools (Cursor, Copilot, raw Claude Code) smarter. Ambient dependency = sticky retention without lock-in.

## Workspace Onboarding Flows

Two paths converge to the same outcome: a workspace with rich context in Direction Stack + CLAUDE.md + `.rorca/`.

### Greenfield (No Existing Code)
1. "New Project" in Rorca → create git repo
2. Choose convention pack (or blank) → scaffolds project structure, CLAUDE.md, `.rorca/`
3. Direction Stack auto-populated from pack (L1 engineering, L2 domain, L3 project)
4. Write brief → spec generation has full context
5. Pipeline runs against a structured, convention-rich project

**Key**: Scaffolding step BEFORE first spec. Story 1 implements features, not project setup. Without a pack, Story 1 must choose framework + scaffold + implement — fragile and prone to convention drift across later stories.

### Brownfield (Existing Codebase / GitHub Fork)
1. Fork/clone repo
2. "Add Workspace" in Rorca → point to directory
3. Automatic context extraction: reads codebase → generates L3, CLAUDE.md (if missing), AGENTS.md
4. Human reviews extracted conventions (approve/edit/reject — same flow as spec review)
5. Write brief → fully context-aware spec generation
6. Pipeline runs with deep understanding of existing project

**Key**: Convention extraction (bottom-up) vs convention injection (top-down for greenfield).

| | Greenfield | Brownfield |
|---|---|---|
| Direction | Top-down — inject conventions from pack | Bottom-up — extract conventions from codebase |
| Source of truth | Convention pack chosen by user | Existing codebase analyzed by agent |
| CLAUDE.md | Generated from pack template | Generated from codebase analysis |
| First story | Implements feature (scaffold exists) | Implements feature (codebase exists) |

## Convention Pack System

**Status**: Not built. Planned as `rorca-convention-packs` spec (post-CIE).

Convention packs are the "framework" for AI-assisted development. Like Next.js encodes web conventions, packs encode development conventions for Rorca. The core insight (Terraform analogy): the hard part isn't the tooling — it's the lack of conventions. Every team reinvents project structure, patterns, and standards. Packs encode those decisions.

### Pack Structure
```
packs/<pack-name>/
├── pack.json                # Metadata, compatibility, dependencies
├── direction/
│   ├── L1-engineering.md    # Engineering principles
│   └── L2-domain.md         # Domain conventions (e.g. SaaS, CLI, mobile)
├── personas/                # Agent persona definitions (see Agent Persona System)
├── conventions/             # Per-library convention guides (tailwind.md, prisma.md, etc.)
├── templates/               # Spec templates for common features (auth, billing, CRUD)
├── scaffold/                # Project scaffolding files (boilerplate, config)
└── AGENTS.md                # File governance template for this stack
```

### Lifecycle (API-first)
All pack operations are Express API routes with `@swagger` annotations → available as MCP tools automatically via OpenAPI-to-MCP generation.
- `POST /api/packs/install` → populates `.rorca/` + Direction Stack + scaffold
- `POST /api/packs/fork` → customize a community pack (workspace-local copy)
- `GET /api/packs` → list installed packs
- `DELETE /api/packs/:name` → uninstall pack + clean up direction layers
- Community packs shared via Marketplace panel (extends existing `marketplace_templates` table)
- Pack conventions are **L0** (lowest priority, overridable by L1+)
- UI-primary: Marketplace panel for browsing/installing. MCP tools auto-generated from the same API routes for Claude Code session access. No separate CLI package to maintain.

### Convention Inference (Brownfield Alternative)
`rorca conventions discover` — agent analyzes existing codebase:
1. Reads package.json, config files → identifies stack
2. Scans file structure → infers architecture
3. Reads existing CLAUDE.md/README → extracts conventions
4. Analyzes code patterns → generates convention observations
5. Produces Direction Stack L3 + CLAUDE.md + AGENTS.md
6. Human reviews before use (approve/edit/reject)

### Convention Drift Detection
`rorca conventions check` — compares current code against declared conventions. Like `terraform plan` for development patterns. Can run as pre-execution pipeline hook. Reports drift: "L2 says 'always use Prisma' but `legacy.ts` uses raw SQL."

## Agent Persona System

**Status**: Not built. Planned as `rorca-agent-personas` spec (post-CIE).

Every story currently runs with the same prompt personality. The persona system assigns specialized agent identities to stories and review passes.

### Persona Categories

**Primary** (1–5 orchestrators):
- **Architect** — structural decisions, dependency graphs
- **PM** — brief → spec translation, story prioritization
- **Lead Dev** — implementation orchestration

**Adversarial** (sub-agents that challenge):
- **Red Team** — attack vector discovery, security scanning
- **Assumption Buster** — "the idiot in the room" — challenges implicit assumptions
- **Devil's Advocate** — argues against proposed approaches

**Specialist** (20-30 domain experts, sub-agents):
- Frontend, Backend, Database, Security, SRE, UX Designer, QA

**Review** (quality gates):
- **Spec Writer** — generates exhaustive, detailed specs
- **Spec Verifier** — consistency checks, dependency validation
- **Best Practices** — library/framework convention enforcement

```
│   ├── frontend.md
```

### Attachment to Stories
```json

  "id": "US-007",
  "title": "Add Stripe webhook handler",
  "persona": "backend",
  "reviewers": ["security", "red-team"]
}
```

Execution engine runs story with `backend` persona, then runs review passes with `security` and `red-team` against the diff. `buildPrompt()` in `execution-engine.ts` injects persona file as additional context layer.

### Review Pipeline (Adversarial Agents)
After implementation, before merge:
```
Story diff → [Security persona] → flags issues
           → [Red Team persona] → adversarial review
           → [Best Practices persona] → convention compliance
           → Results aggregated in story_comments table
```
Each reviewer can flag blocking issues that prevent story from passing.

## Multi-Pass Spec Generation Pipeline

**Status**: Not built. Planned as `rorca-spec-pipeline` spec (post-agent-personas).

Current spec generation: one LLM call. Proposed: 6 sequential agent passes, each refining the previous output. Goal: specs so detailed that a blind person can implement them — every state, every edge case, every button label explicit.

```
Pass 1: PM Agent
  Brief → high-level spec (10-20 stories, coarse)

Pass 2: Spec Writer Agent
  Each story → decomposed into micro-stories (exhaustive granularity)
  "Add auth" → 15 atomic tasks: schema, middleware, login route, token refresh,
  password reset, email verification, rate limiting, session management, logout,
  CSRF protection, input validation, error messages, success states, loading states,
  empty states

Pass 3: UX Designer Agent
  Each story → explicit visual descriptions
  Text models can't see — describe EVERYTHING: button labels, field names,
  layout positions, loading spinners, empty state copy, error message text

Pass 4: Best Practices Agent
  Each story → library convention annotations
  "Use Tailwind space-y-4 not manual margin. Use shadcn/ui Button, not raw <button>."
  Auto-generated from convention pack or extracted conventions

Pass 5: Adversarial Review (Assumption Buster + Devil's Advocate)
  Review entire spec for: contradictions between stories, missing edge cases,
  implicit assumptions, missing error/loading/empty states

Pass 6: Spec Verifier
  Final consistency check: acceptance criteria are testable, no circular deps,
  every dependsOn target exists, no orphaned stories
```

Forge panel shows progress through passes. Each pass creates a spec version (tracked in `spec_versions`). Human reviewer sees full audit trail: which persona added/modified what.

### Why Exhaustive Granularity Matters
Text models produce text, not visuals. A spec that says "add a login page" forces the implementing agent to make 50 implicit decisions. A spec that says "add a login page with email field (placeholder: 'you@example.com'), password field (type=password, show/hide toggle), submit button (label: 'Sign in', disabled while loading, shows spinner), 'Forgot password?' link (navigates to /forgot-password), error toast on 401 (message: 'Invalid email or password')" produces deterministic output across any model or agent.

- **vs MetaGPT**: Academic research project, no UI, no production pipeline
- **vs Cursor/Windsurf**: IDE assistants, not spec orchestrators — no pipeline, no direction stack, no autonomous multi-story execution
- **"Spec-driven development"** is unclaimed terminology — no Google results, blue ocean category to own

**Core moat (3 layers):**
1. Direction stack — persistent context cascade across all stories (L1–L5)
2. Per-story subprocess isolation — infinite effective context, runs to completion
3. Triple execution engine — `claude --print` (Claude sub) + `opencode run` (75+ providers) + `codex` (ChatGPT sub) — same tool set, same quality, user chooses their model

**The brand statement**: "Every story runs as a fresh isolated subprocess with the full tool set — bash, edit, read, write, glob, grep. No context limits. A spec can run forever. That's the Rorca engine."

## Wave-Based Parallel Execution

**Status**: Built. Wave parallel is opt-in per run (toggle in spec detail slide-over). Sequential is still the default.

**The idea**: Instead of running stories one-by-one, compile the `dependsOn` DAG into topological wave groups. Each wave runs its stories in parallel git worktrees, then auto-merges before the next wave starts.

```
Wave 0 (no deps):  US-001, US-002, US-003 → 3 parallel worktrees → merge
Wave 1 (deps on wave 0): US-004, US-005 → 2 parallel worktrees → merge
Wave 2: US-006 → 1 worktree → merge → done
Sequential: 40 min total  →  Wave parallel: ~12 min (3.3x speedup on 3-wave spec)
```

**How it works**: Wave compiler does a topological sort of the `dependsOn` DAG into wave groups. Each wave runs its stories in parallel git worktrees. Auto-merge fires after each wave before the next starts. Configurable max parallelism (default 20). Toggle visible in the spec detail slide-over — shows wave breakdown before you run.

### Database (`backend/src/db/`)
- **Owner**: Database specialist
- **Rules**:
  - PostgreSQL 16 via `pg` Pool — all DB calls are **async** (always `await`)
  - `query<T>()` → `T[]`, `queryOne<T>()` → `T | undefined`, `execute()` → `{ rowCount }`
  - Migrations are SQL in `pg-migrations/`, numbered sequentially (001–062+), tracked via `schema_migrations` table
  - Use `$1, $2, ...` numbered placeholders (NOT `?`)
  - FK constraints always on, connection pooling (max 20)
  - **pgboss schema is NOT hand-managed** — `pgboss.*` tables (job, archive, subscription, version) are created and upgraded automatically by `boss.start()`. Never write migrations that touch `pgboss.*`. Migration 062 is a no-op placeholder that documents this.
  - **pg-boss v10 requires explicit queue creation** — `boss.work('queue:name', handler)` does NOT create the queue or its partition table. You MUST call `await boss.createQueue('queue:name')` before calling `boss.send('queue:name', ...)`, otherwise `send()` returns `null` silently. The `job` table is partitioned by queue name (one partition per queue). In tests, call `createQueue` in `beforeAll` after `boss.start()`.
  - **pg-boss job `id` must be a valid UUID** — passing an integer string (e.g., `String(runId)`) to the `id` option of `boss.send()` causes a PostgreSQL UUID cast error. Use auto-generated UUIDs (omit the `id` option) and embed `runId` in the job's data payload for correlation.

### Spec Path Construction (CRITICAL — has caused bugs)
```typescript

// CORRECT
```

### spec.id vs spec.specName
- `spec.id` = filename slug (`rorca-feature-enhancements`) — use for API calls and paths

### chatComplete Return Type

### Stale Pipeline Runs

# Adversarial Thinking

Apply systematic adversarial thinking patterns to challenge assumptions, identify weaknesses, and improve decision quality through multiple complementary adversarial perspectives.

## When to use me

Use this skill when:
- Making high-stakes decisions with significant consequences
- Designing systems that must withstand real-world challenges
- Preparing for security reviews, audits, or compliance checks
- Building resilience against failures, attacks, or market changes
- Preventing groupthink and confirmation bias in teams
- Stress-testing ideas, designs, or implementations
- Improving system security and robustness
- Developing critical thinking skills across the organization
- Preparing for competitive environments or adversarial conditions

## Adversarial Thinking Framework

Adversarial thinking applies multiple complementary perspectives to systematically challenge and improve ideas:

### 1. **Devil's Advocate** (@skills/devils-advocate)
- **Purpose**: Challenge ideas through logical counterarguments and alternative perspectives
- **Focus**: Logical reasoning, argument quality, alternative explanations
- **When to use**: Decision-making, proposal evaluation, preventing groupthink
- **Output**: Counterarguments, weaknesses, alternative approaches

### 2. **Assumption Buster** (@skills/assumption-buster)
- **Purpose**: Aggressively identify and disprove assumptions through counterexamples
- **Focus**: Finding where assumptions fail, edge cases, failure modes
- **When to use**: Critical systems, high-failure-cost scenarios, risk assessment
- **Output**: Busted assumptions, failure scenarios, risk areas

### 3. **Red Team** (@skills/redteam)
- **Purpose**: Think like an attacker to identify security vulnerabilities
- **Focus**: Security weaknesses, penetration vectors, attack paths
- **When to use**: Security assessments, penetration testing, defense preparation
- **Output**: Vulnerabilities, attack simulations, security recommendations

### 4. **White Hat** (@skills/white-hat)
- **Purpose**: Build defensive security capabilities and implement security by design
- **Focus**: Protective controls, security architecture, ethical testing
- **When to use**: Security implementation, compliance, defense building
- **Output**: Security controls, defense recommendations, security posture

### 5. **Trust But Verify** (@skills/trust-but-verify)
- **Purpose**: Independently verify claims rather than trusting assumptions
- **Focus**: Evidence validation, claim verification, reality checking
- **When to use**: Validating test results, progress claims, system capabilities
- **Output**: Verification results, discrepancies, confidence assessments

## Integrated Adversarial Thinking Workflow

### Phase 1: Challenge Foundation
1. **Devil's Advocate**: Challenge core ideas and reasoning
2. **Assumption Buster**: Identify and test foundational assumptions
3. **Trust But Verify**: Validate evidence and claims

### Phase 2: Stress Test Design
1. **Assumption Buster**: Find edge cases and failure modes
2. **Red Team**: Identify attack vectors and security weaknesses
3. **Devil's Advocate**: Challenge design decisions and alternatives

### Phase 3: Build Defenses
1. **White Hat**: Implement security controls and defenses
2. **Trust But Verify**: Validate defensive effectiveness
3. **Devil's Advocate**: Challenge defense completeness

### Phase 4: Continuous Improvement
1. **Trust But Verify**: Monitor and validate ongoing
2. **Red Team**: Regular security testing
3. **Assumption Buster**: Periodic assumption review

## When to Use Which Adversarial Perspective

### For Technical Decisions:
- **Architecture choices**: Devil's Advocate + Assumption Buster
- **Technology selection**: Devil's Advocate + Trust But Verify
- **Implementation details**: Assumption Buster + White Hat
- **Security design**: Red Team + White Hat

### For Product Decisions:
- **Feature prioritization**: Devil's Advocate + Assumption Buster
- **User experience**: Assumption Buster + Trust But Verify
- **Market strategy**: Devil's Advocate + Red Team (competitive analysis)
- **Business model**: Assumption Buster + Trust But Verify

### For Security Assessments:
- **Penetration testing**: Red Team primary, White Hat secondary
- **Security architecture**: White Hat primary, Red Team secondary
- **Incident response**: White Hat primary, Trust But Verify secondary
- **Compliance**: White Hat primary, Devil's Advocate secondary

### For Risk Management:
- **Risk identification**: Assumption Buster primary
- **Risk assessment**: Trust But Verify primary
- **Risk mitigation**: White Hat primary
- **Risk monitoring**: Trust But Verify primary

Your task (CLI-047):
**SECURITY + LICENSING CRITICAL.** Today, every Express route with a @swagger annotation is automatically exposed as an MCP tool (mcp-http.ts:372-432). 418 @swagger annotations across 60+ route files = ~414 auto-promoted tools.

**Original Aegis design** used `x-mcp-tier` (3 values: public/admin/denied) — this was MCP-only. **Open-core pivot upgrades this** to a unified `x-rorca-tier` annotation with 4 values that simultaneously controls (a) MCP exposure, (b) the open-source CLI's allowed surface, (c) the proprietary backend's plan-gating boundary.

**The 4-tier model**:

| Tier | Who can call | Examples |
|------|------|------|
| `public` | CLI/MCP/web (no auth required) | Spec CRUD, story execution, local memory, recall, search |
| `auth` | Logged-in users only | Personal profiles, owned workspace settings, user prefs |
| `paid` | Paid subscription only | Team RBAC, federated memory, GRC audit traces, multi-entity accounting, FinOps |
| `admin` | Local single-user admin | Backups, license generation, embed-all, db migrations |
| (no annotation) | Default DENIED — never MCP, server returns 404 in opt-in mode | All other routes |

**Step 1 — Define annotation contract** in `backend/src/lib/tier-auth.ts` (NEW file — replaces the originally-planned mcp-auth tier code):
```typescript
export type RorcaTier = 'public' | 'auth' | 'paid' | 'admin';
export type RorcaTierOrDenied = RorcaTier | 'denied';

export interface RorcaTierMetadata {
  tier: RorcaTierOrDenied;
  rationale?: string;  // Required for non-denied — visible in code review
  publicApi?: boolean;  // True if this is part of the open-source CLI's stable API contract
}

export function getRorcaTier(operation: { 'x-rorca-tier'?: string; 'x-rorca-rationale'?: string; 'x-rorca-public-api'?: boolean }): RorcaTierMetadata {
  const raw = operation['x-rorca-tier'];
  if (raw === 'public' || raw === 'auth' || raw === 'paid' || raw === 'admin') {
    return {
      tier: raw,
      rationale: operation['x-rorca-rationale'],
      publicApi: operation['x-rorca-public-api'] === true,
    };
  }
  return { tier: 'denied' };
}

export function tierAllowedFromMcp(tier: RorcaTierOrDenied): boolean {
  // MCP exposes only public + auth tiers. PAID and ADMIN are never MCP-callable
  // (LLMs should never trigger billing or backups, even with admin token).
  return tier === 'public' || tier === 'auth';
}
```
