Task (US-014): Embedded TUI: Live Run View with Per-Story Output Streaming
Implement a live run view in ~/.pi/agent/extensions/rorca/tui/run-view.ts showing wave execution progress, per-story status updated via polling, and an inline output pane for the focused story's stdout stream. Handles wave structure, merge status between waves, cancellation, and detach-without-cancel.

## Context
- **File location & export**: Must be at `~/.pi/agent/extensions/rorca/tui/run-view.ts` with exact signature `async function openRunView(pi: ExtensionAPI, runId: number, baseUrl: string, token?: string): Promise<void>`. Follow the extension API patterns established in US-007's `spec-orchestrator.ts` and US-011's status widget for consistent `pi.term` usage.
- **Wave structure from spec-orchestrator**: Import `buildWaves()` from `spec-orchestrator.ts` (US-007) for topological wave grouping. The spec JSON uses `userStories` (NOT `stories`) and story IDs follow the `US-XXX` slug format. Fall back to flat list if spec file at `workspacePath/forge/specs/approved/{specId}.json` is inaccessible — do not crash.
- **API endpoints & auth**: All fetches to `/api/pipeline/runs/{runId}` and story output endpoints must include `Authorization: Bearer ${token}` header when token is provided. The MCP token lives at `~/.rorca/mcp-token`. Per-story output endpoint (`/api/pipeline/runs/{runId}/stories/{storyId}/output`) may not exist yet — verify against `backend/src/routes/` before implementing; the current output SSE is per-run (`/api/pipeline/runs/:runId/output`), not per-story. The `run_output_chunks` table has no `story_id` column (known bug in memory), so per-story filtering may need to be scoped differently or this AC may require a backend addition.
- **Polling over SSE in Pi context**: Pi extensions likely cannot hold open SSE connections reliably. Prefer polling with 2–3s intervals. Use `pi.term` for all terminal output — do not write directly to `process.stdout`. Targeted ANSI cursor repositioning (`\x1b[{row};{col}H`) for in-place status updates is correct but ensure the terminal is in raw mode and track row offsets carefully when wave count changes (e.g., merge status lines inserted).
- **Cancel endpoint**: The cancel route is `POST /api/pipeline/runs/:runId/cancel` which inserts a `pipeline:cancel` pg-boss job. It does not cancel synchronously — the worker picks up the job and sends SIGTERM. Continue polling until `status === 'cancelled'` or `status === 'failed'`.
- **Detach-without-cancel**: On `q`, must clean up all polling intervals/timers before returning. Do NOT call `clearActiveRun()` from US-011's status widget — the run continues in background and the status widget should keep showing progress until the run finishes naturally.
- **Memory: sse-hub is process-local**: Do not rely on SSE hub broadcasts reaching this extension. The worker and API server are separate processes — DB-backed `run_output_chunks` polling is the reliable path for output streaming, not in-memory SSE subscriptions.
- **ANSI blinking caveat**: `\x1b[5m` (blink) is not supported by all terminals. Consider a fallback like bold+yellow (`\x1b[1;33m`) for "running" status if blink is not rendered. Keep all ANSI sequences behind a helper function for consistency with other TUI files in the extension.
